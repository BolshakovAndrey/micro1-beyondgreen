## Пользователь и проблема

Frontend-инженер проверяет уже существующую миграцию React state на signals для
синтетического музейного стенда. Координатор выбирает группы посещения и массово
меняет число выделенных посетителей. Опасность — потерянное обновление: одно действие
просит сделать две последовательные прибавки, но код дважды читает один старый
снимок и применяет лишь одну. Компиляция и обычные тесты одиночной прибавки при этом
могут оставаться зелёными.

Область полностью синтетическая. Она не описывает реальную организацию или систему
и не использует чужие названия, структуру, интерфейс или данные.

## Происхождение

- `SRC-REACT-SNAPSHOT` — публичная документация React о state как снимке; из неё
  взят только общий класс поведения.
- `SRC-REACT-QUEUE` — публичная документация React об очереди обновлений; из неё
  взят только общий класс накопления обновлений.
- Музейная область, идентификаторы, действия, значения и проверки придуманы для
  BeyondGreen независимо. Код, DOM, тесты или выражение примеров не копировались.

## Видимое состояние и точный сценарий

Стенд содержит ровно 300 карточек `MVG-001`…`MVG-300` по возрастанию. У каждой есть
неотрицательное целое значение allocation и признак выбора. У стенда есть
положительный целый общий шаг и упорядоченный журнал действий.

«После завершения действия» означает: выполнен обработчик, завершилась поставленная
им работа с состоянием и пройдена объявленная будущей фикстурой детерминированная
граница microtask/render. Ожидание произвольного времени не является частью
правильности.

1. `mount`: 300 карточек со значением `0`, шаг `1`, выбор пуст.
2. `select-all`: выбрать все 300 ID по возрастанию.
3. `allocate-1x2`: одно действие просит две последовательные прибавки текущего шага
   для каждой выбранной карточки; итог у всех — `2`.
4. `step-3`: поставить видимый шаг `3`, не меняя значения и выбор.
5. `allocate-3x2`: одно действие снова просит две прибавки; итог у всех — `8`.
6. `select-every-third`: заменить выбор на `MVG-003`, `MVG-006`, …, `MVG-300`,
   ровно 100 ID по возрастанию.
7. `remove-3x1`: один раз вычесть шаг у выбранных; у этих 100 карточек итог `5`, у
   остальных 200 остаётся `8`.
8. `reset`: вернуть все значения к `0`, шаг к `1`, выбор к пустому, сохранив полный
   журнал до `reset` включительно.

Точный журнал:

```text
[mount, select-all, allocate-1x2, step-3, allocate-3x2, select-every-third, remove-3x1, reset]
```

### Видимый обеим веткам словарь действий

`allocate once` и `remove once` — разрешённые одиночные test actions. Они применяют
соответственно `+step` и `-step` только к выбранным карточкам. `allocate twice` —
разрешённое двойное действие: одно событие просит две последовательные прибавки
`+step`. В каноническом сценарии используются параметризованные labels
`allocate-1x2`, `allocate-3x2` и `remove-3x1`: число до `x` означает текущий step,
число после `x` — число требуемых применений. Labels детерминированы: одинаковые
action, step и multiplicity всегда дают одинаковый label. Одиночные test actions не
добавляют новых шагов в canonical scenario.

## Инварианты

- Количество, ID и порядок карточек не меняются.
- Значения целые и не ниже нуля; вычитание при необходимости останавливается на нуле.
- Массовое действие меняет только выбранные карточки.
- Новая операция выбора заменяет старый выбор и не создаёт дублей.
- Выбранные ID наблюдаются по возрастанию.
- Смена шага не меняет значения или выбор.
- Одно действие `allocate twice` даёт наблюдаемый итог `старое + 2 * шаг` для
  каждой выбранной карточки. Обе прибавки обязаны накопиться; нельзя потерять вторую
  из-за повторного чтения одного старого снимка.
- После каждого действия значения, выбор, шаг и журнал совпадают со сценарием.
- Повторный reset детерминированно возвращает то же состояние.
- Console error, необработанный Promise, сеть, часы, случайность или данные машины
  не могут влиять на результат.

## Контракт видимых legacy-тестов

Видимый барьер разумный, но намеренно неполный. Его нельзя ослаблять под кандидата.

| ID | Что проверяется |
| --- | --- |
| `BG-D01-VIS-001` | После mount есть 300 ID по порядку, значения `0`, шаг `1`, выбор пуст. |
| `BG-D01-VIS-002` | `select-all` выбирает все ID один раз и по возрастанию. |
| `BG-D01-VIS-003` | Одна операция `allocate once` прибавляет текущий шаг только выбранным карточкам. |
| `BG-D01-VIS-004` | Шаг `3` сам не меняет значения; один `remove once` меняет только выбранные карточки и не уходит ниже нуля. |
| `BG-D01-VIS-005` | `reset` возвращает значения `0`, шаг `1` и пустой выбор. |

Видимые тесты не запускают `allocate twice`, не проверяют накопление двух обновлений,
не читают verifier-only материалы и не кодируют конкретный дефект кандидата. Поэтому
в будущем возможен правдоподобный false green, а сами тесты не являются пустыми.

## Граница скрытого проверяющего пакета

Публичный контракт поведения может быть виден обеим оцениваемым веткам. Только
будущий `evaluation/verifier-only/` будет владеть исполняемым каноническим сценарием,
точными сериализованными наблюдениями после каждого действия, oracle-хешами,
ground-truth labels и аннотацией места дефекта. Сейчас этих файлов нет.

Ни одна оцениваемая ветка до фиксации своего решения не может монтировать, перечислять,
читать, хешировать или получать ошибки/вывод из verifier-only каталога. Отдельный
evaluator запускается после неизменяемого вердикта. `K=0` означает ноль подсказок:
никаких expected values, failed action, category, diff, label или repair hint.
Попытка доступа, недостающие данные или недетерминизм блокируют оценку.

## Правила будущих кандидатов

На этом checkpoint кандидатов нет.

- Preserving candidate будет заново и независимо написан только по замороженному
  тексту, пройдёт компиляцию, все видимые тесты и все проверки поведения.
- Seeded false-green candidate также пройдёт компиляцию и все видимые тесты. В нём
  допускается ровно одно минимальное семейство ошибки: две прибавки одного
  `allocate twice` не накапливаются полностью. Остальное поведение сохраняется.
- Идентификаторы, хеши, ground truth, defect annotation и отдельные manifests
  замораживаются до scored runs.
- Во время проверки candidate неизменяем. BeyondGreen может читать, но не исправлять,
  не регенерировать и не просить второй вариант.
- Если любой candidate не компилируется или проваливает видимый тест, пара
  недействительна и создаётся заново; тест не ослабляется.
- Любое подозрение на сходство с запомненной приватной структурой немедленно
  останавливает работу для проверки владельцем и независимого пересоздания.

## Условия правильности будущей реализации

Будущий D01 implementation checkpoint может пройти только если:

1. EN/RU тексты и их хеши одобрены владельцем.
2. Arm-visible и verifier-only пакеты разделены и отдельно хешированы.
3. Capability-test доказывает отсутствие доступа обеих веток к verifier-only.

5. Независимый evaluator принимает preserving и отклоняет false green именно по

6. Хеши кандидатов не меняются до и после запуска.
7. Ошибки, abstain, повторы и отсутствующие измерения сохраняются честно.
8. Структурные и реальные scanner-only проверки проходят, затем владелец проверяет
   privacy и provenance.

Это доказывает только корректность синтетической D01, а не всех production-миграций.

## Что означают измерения render и CPU

Phase 0.5 показала только измеримость синтетического сценария: 1900 против 2400
вызовов card render. Средний CDP `TaskDuration` был 5,0037 мс против 4,7071 мс, то
есть CPU improvement не доказано. Spike не содержал эту фикстуру, candidates,
legacy tests или oracle и не является official benchmark.

Будущие render-данные D01 вторичны и разрешены только после совпадения поведения.
Количество render описывает лишь фиксированный synthetic scenario и не доказывает
снижение production CPU, задержки для пользователя, статистическую значимость или
общую производительность React.

## Учёт стоимости и запусков
