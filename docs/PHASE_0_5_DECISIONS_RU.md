**Статус фиксации:** закрыто в `2026-08-29T13:41:51Z` с явным исключением для
вложенного CLI; product implementation не разрешён. Координатор подтвердил последнее
условие: 60 Chromium-измерений (по 30 на ветку), неизменные порядок и N=300, полный

является провалом gate. Два CLI-отказа остаются отказами; live runtime не доказан.

## Результат измеряемой проверки — принят для фиксации

Одобренные измерения Phase 0.5 завершены и зафиксированы с учётом явного решения
владельца пропустить вложенную CLI-проверку в desktop-среде. Два отказа `codex exec` остаются
отказами: работа CLI здесь не доказана. Работа Sol, которую владелец наблюдает в
текущем приложении, — только контекст владельца, а не доказательство для submission.
Необязательный адаптер для обычного терминала сохраняет правило без повторов.
Единственный проверенный путь воспроизводимости — детерминированный offline replay;
он повторяет сохранённые события, но не доказывает живую работу модели.

Независимый Chromium-сценарий с музейной доской прошёл барьер правильности в
`Chrome/152.0.7977.64`: после каждого действия совпали все значения и выбранные ID
для 300 карточек, упорядоченный журнал и его хеш, а также сброс. Ошибок console и
необработанных исключений — 0. Финальный отчёт содержит 5 прогревов и 30 измерений

улучшенной, поэтому ускорение CPU не заявляется. Первый запуск сохранил только

### Почему текущая попытка остановлена

Точные одобренные версии добавлены. Команды `npm install --package-lock-only
--ignore-scripts` и `npm ci --ignore-scripts` завершились; вторая установила 54

вывел машинный внешний путь к debug-log. Этот путь не открывался, не копировался и
не сохранялся; из будущей submission-траектории его нужно удалить как машинные
данные.

Это обязательная остановка по dependency/license и trace-redaction gate. Повтор не
делался. После ошибки не запускались проверки десяти классов поведения, модель,

## 3. Живой reasoning engine и запасной replay

Основной живой транспорт — локальная уже авторизованная сессия `codex exec` за общим,
нейтральным к поставщику интерфейсом. Предлагаемый адаптер
`codex-exec-jsonl-v1` использует уже найденный `codex-cli 0.148.0`. Он запускается из
доступного модели корня кандидата и получает запрос через stdin:

```text
codex exec --ephemeral --ignore-user-config --json --output-schema <schema> --sandbox read-only --model gpt-5.6-sol
```

Все флаги уже подтверждены сохранённым выводом `codex exec --help`. `<schema>` —
зафиксированный относительный путь к схеме решения внутри репозитория.
`--ephemeral` не сохраняет сессию, `--ignore-user-config` исключает личные настройки,
JSON events и `--output-schema` дают машинно читаемый ответ, `--sandbox read-only`
запрещает модели записи. Координатор проверил `codex login status` и получил
`Logged in using ChatGPT`: используется эта авторизованная через подписку CLI-сессия,
отдельный ключ не требуется. Кандидат модели — `gpt-5.6-sol`: на 2026-08-29 текущая
линейка называет GPT-5.6 Sol флагманской моделью для сложной профессиональной работы.
При фиксированной цене подписки нет причины выбирать модель ради экономии на каждом
вызове. Spike проверяет, доступен ли Sol в текущей ChatGPT-авторизованной CLI-сессии
и как он себя ведёт. Искать или молча подставлять другую модель запрещено; если Sol
недоступен, работа останавливается для решения владельца.

На кандидата разрешён один вызов модели, ноль повторов модели и ноль повторов
транспорта. Адаптер отвечает за одинаковое чтение JSONL/events, проверку финального
ответа по схеме, timeout, операционный `abstain` (честный отказ вынести вердикт) и
перевод в replay из решения 5. Будущий spike должен проверить повторяемое чтение
events, правильный финальный JSON, read-only sandbox, timeout, ошибку недоступной
модели, отсутствие повторов и offline replay. Модель получает только разрешённые
материалы ветки; скрытый oracle и пути проверяющей стороны передавать нельзя. Claude
разрешён только для read-only review и запрещён как движок решения.

Запасной путь — детерминированное, то есть дающее одинаковый результат на одинаковых
данных, воспроизведение `offline-replay-jsonl-v1`. Если авторизованная CLI-сессия или
модель-кандидат недоступна, оно может проверить чтение записей, учёт лимитов, отчёты и
повторяемость на ранее одобренных публичных/синтетических записях. Оно не создаёт
живое зачётное доказательство и не заменяет обязательную проверку с моделью. Тогда
реализация остаётся заблокирована, если владелец отдельно не одобрит честный режим
только offline.

## 4. Контроль бюджета и времени

Авторизованная сессия Codex оплачивается фиксированной подпиской. Надёжная добавочная
стоимость одного кандидата в долларах недоступна, поэтому в доказательства пишется
`marginal_usd_cost: not_measured` — не ноль и не оценка. Лимит в долларах не
заявляется. Токены записываются только если CLI во время spike сообщает их явно и
стабильно; иначе записывается `token_usage: not_measured`.

Технически проверяемый бюджет — ровно один вызов на кандидата, ноль повторов модели,
ноль повторов транспорта и ограничение времени. Второй вызов или повтор считается
нарушением протокола, а не способом исправить ответ.

Общий предел остаётся 180 секунд. Внутренний срок адаптера — 165 секунд, последние
15 секунд оставляются на проверку ответа, сохранение доказательств и чистое
завершение. Истечение времени, неверный формат, запрос второго
вызова или недоступная модель дают операционный `abstain`, а не попытку исправления.
До одобрения транспорта spike должен проверить все эти ограничения.

## 5. Версионное детерминированное offline-воспроизведение

Предлагаемый идентификатор формата — `beyondgreen-replay-jsonl@1.0.0`. Файл имеет
кодировку UTF-8, строки LF, не содержит byte-order mark и хранит по одному объекту
RFC 8785 JSON Canonicalization Scheme в строке. Допустимый порядок `record_type`:
`header`, одна или несколько пар `model_request`/`model_response`, затем
`decision_input`, `decision_output`, `footer`.

Каждая запись содержит `schema_version`, непрерывный номер `sequence` от нуля,
`record_type`, `created_at_utc`, `run_id`, `fixture_id`, `candidate_id`, `arm_id`,
`candidate_sha256`, `policy_sha256`, `adapter_id`, `adapter_version`, `model_id`,
`previous_chain_sha256` и `record_sha256`. Запрос и ответ дополнительно содержат
`request_id`, точные видимые ветке данные или ответ, статус учёта токенов,
`marginal_usd_cost`, причину завершения и время. Значения токенов и стоимости следуют
решению 4 и могут быть `not_measured`; придумывать их запрещено. `created_at_utc` сохраняется как факт, но
не участвует в сравнении смыслового результата.

`record_sha256` — SHA-256 канонической RFC 8785 записи без самого поля
`record_sha256`. Первый `previous_chain_sha256` равен 64 нулям; каждый следующий —
`SHA256(previous_chain_sha256 + "\n" + previous record_sha256)`. В `footer`
записываются итог цепочки и SHA-256 упорядоченных канонических записей до `footer`.

Воспроизведение принимается только при точном совпадении кодировки, схемы/версии,
порядка и номеров записей, каждого хеша, цепочки, итогового хеша, идентификаторов,
зафиксированных хешей кандидата/политики/модели/адаптера и соответствия каждого
запроса одному ответу. Сеть и запуск процессов отключены, рабочая область не
изменяется. Повтор должен создать побайтно одинаковые нормализованные JSON решения
и хеши отчётов с тем же вердиктом и ссылками на доказательства. Replay не считается
и не создаёт зачётную попытку.

Нельзя воспроизводить или раскрывать скрытый oracle, обратную связь оценщика до
решения, пути только для проверяющей стороны, секреты, значения окружения, приватные
или машинные пути, результаты held-out случаев или данные приватных систем. Нельзя
делать новый вызов модели, выполнять записанные команды, исправлять ответ, создавать
вторую попытку, менять доказательства или вердикт.

## 7. Сценарий Chromium с приоритетом корректности

Первый предлагаемый сценарий — `BG-D01`, полностью независимо придуманный
синтетический **стенд распределения музейных групп по посещениям**. Пользователь
увидит обычную CSS-сетку из 300 карточек `MVG-001`…`MVG-300`. На каждой карточке
показано число посетителей и выбрана ли группа. Этот сценарий не использует приватный
код, названия, структуру, layout или данные. Точную версию Chromium нужно записать и
зафиксировать во время измеряемого spike; сейчас браузер не запускался.

Для каждого измерения создаётся новый контекст браузера: 1280x720, device scale
factor 1, reduced motion включён, сеть отключается после загрузки локальной страницы.
Для эталона и кандидата выполняются одинаковые действия:

1. Показать 300 карточек со значением `0`, шагом `1` и без выбранных групп.
2. Нажать `Select all`; требовать выбранные ID от `MVG-001` до `MVG-300` по порядку.
3. Один раз нажать `Allocate twice`. Одно пользовательское действие ставит в очередь
   два обновления каждой выбранной карточки из одного начального снимка. После
   микрозадач и одного кадра все 300 значений должны стать `2`. Так ловится D01:
   ошибка устаревшего снимка потеряет одно из двух обновлений.
4. Поставить видимый общий шаг `3` и один раз нажать `Allocate twice`; все 300
   значений должны стать `8`.
5. Нажать `Select every third`; должны быть выбраны ровно 100 ID: `MVG-003`,
   `MVG-006`, …, `MVG-300`.
6. Нажать `Remove once`; у этих 100 карточек должно стать `5`, у остальных 200 — `8`.
7. Нажать `Reset`; все 300 значений должны стать `0`, шаг — `1`, выбор — пустым.

Baseline (обычная исходная ветка) и advanced arm (ветка с расширенной проверкой)
имеют одинаковые DOM и наблюдаемые правила на каждом шаге. Проверка сохраняет все
300 ID и значений по порядку после каждого массового действия, выбранные ID,
журнал `[mount, select-all, allocate-1x2, step-3, allocate-3x2,
select-every-third, remove-3x1, reset]` и SHA-256 канонического JSON. Состояние после
Reset, журнал, хеш, ошибки console и необработанные отклонения Promise обязательны.

Для каждой ветки выполняются пять неучитываемых прогревов, затем 30 измерений:
15 пар `reference → candidate` и 15 пар `candidate → reference`. Сохраняется каждый
результат. Главный показатель перерисовок — явные одинаковые счётчики в коде
сценария: сколько раз отрисован весь стенд, сколько всего раз отрисованы карточки и
сколько раз каждая карточка. Счётчики обнуляются перед окном действий. React Profiler
`actualDuration` можно публиковать только для одинаковой явно названной profiling
build; иначе показатель полностью опускается, а не записывается нулём. CPU измеряется
как разница двух снимков CDP `Performance.getMetrics` `TaskDuration`: сразу до и
сразу после завершившегося окна действий. Накопленное абсолютное значение неверно.
Обычное время вторично. Для каждой ветки публикуются все сырые значения, mean,
median, p95, выборочное стандартное отклонение, коэффициент вариации, minimum,
maximum, версии браузера/среды и порядок запуска.

Корректность — безусловный входной контроль. Все наблюдаемые значения и хеши
доказательств должны совпасть с эталоном во всех измерениях, без ошибок console и
необработанных отклонений. Любое расхождение даёт `behavior_failure`, исключает все
измерения времени/render этого сценария из сравнения и запрещает заявление об
ускорении. Производительность остаётся вторичным доказательством и не влияет на
оценку v1.1.

Нужно записать точную версию Chromium и безопасное публичное описание среды: семейство
и основную версию ОС, архитектуру CPU, число логических ядер и округлённую категорию
RAM. Нельзя записывать hostname, username, серийные/устройственные идентификаторы,
пути и другие машинные идентификаторы. Размер фиксирован: 300 карточек. Если spike
покажет, что протокол невыполним, работа возвращается владельцу; подбирать число
карточек после просмотра результата запрещено.
