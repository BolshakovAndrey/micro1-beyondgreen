# BeyondGreen

**Проверьте миграцию React со state на сигналы, которую ваши тесты уже назвали зелёной.**

Миграция, которая компилируется и проходит все легаси-тесты, всё равно может быть сломана.
BeyondGreen берёт уже существующего неизменяемого кандидата, составляет опись того, что
миграция ставит под угрозу, выводит поведенческие пробы из тех данных, которые плечо
действительно видит, исполняет их против физически изолированного оракула и возвращает
бандл доказательств с решением: принять, отклонить или воздержаться.

> Зелёная компиляция и легаси-тесты — это свидетельство, а не доказательство.

---

## У кого эта проблема

Фронтенд-инженер, который переводит зрелый React-код с состояния в стиле `useState` на
сигналы.

Код достался по наследству, он медленный, а набор тестов, пришедший вместе с ним, писался
под старую реализацию. Эти тесты проверяют, что компонент отрисовывает. Они не проверяют
того, что миграция на сигналы ломает на самом деле: порядок обновлений, стабильность
идентичности, снятие подписок, жизненный цикл, откат.

**Узкое место.** Инженеру надо решить, мержить или нет, а зелёный набор тестов — это
единственный доступный сигнал. Дешёвого способа отличить добросовестную миграцию от той,
что тихо изменила ненаблюдаемый инвариант, не существует. Поэтому команды либо мержат
на надежде, либо оставляют медленный код — и оба исхода стоят реальных денег.

**Почему это стоит решать.** Отказ молчаливый, и он уезжает в продакшн. Всплывает он
позже — потерянным обновлением, устаревшей карточкой, утёкшей подпиской — далеко от
коммита, который его вызвал, где искать причину дороже на порядки.

## Результаты

Десять синтетических фикстур, десять классов поведения, двадцать замороженных кандидатов:
десять сохраняют поведение, десять содержат один посеянный дефект. **Все двадцать
компилируются и проходят сто процентов своих видимых легаси-тестов на момент заморозки** —
именно это делает бенчмарк трудным.

| Метрика | Базовое плечо | BeyondGreen | Цель |
|---|---:|---:|---:|
| Точность решений | `10/20` | `19/20` | ≥ 16/20 — достигнута |
| Преимущество над базовым плечом | — | `+9/20` | ≥ 6/20 — достигнута |
| Полнота обнаружения дефектов с верной причиной | `0/10` | `3/10` | ≥ 8/10 — **не достигнута** |
| Ложные тревоги на сохраняющих кандидатах | `0/10` | `1/10` | ≤ 2/10 — достигнута |
| Завершённость | `20/20` | `19/20` | ≥ 18/20 — достигнута |

Целевые значения объявлены в `docs/EVALUATION.md` до того, как была написана хотя бы одна
фикстура. Там, где цель не взята, публикуется и неизменная цель, и честный результат.
`BG-H02` — асинхронный порядок обновлений — был помечен как трудный случай до того, как
появился его код.

Единственный незавершённый результат — `abstain` (воздержание от решения) на сохраняющем
кандидате `BG-H06`. Замороженный счётчик верной причины засчитал `3/10` через строгий
лексический показатель: нормализованное обоснование должно буквально содержать закрытую
метку класса поведения или неуспешного действия из проверяющего слоя. Семь верных решений
об отклонении не совпали с этим словарём, хотя некоторые объяснения точно описывали дефект.
Поэтому неизменный результат `3/10` измеряет этот узкий операционный показатель, а не все
смыслово верные диагнозы. Полный разбор приведён в `docs/EVALUATION.md`.

## Быстрый старт

Требуется Node `22.22.3` (см. `.node-version`). Рабочие зависимости: React,
`@preact/signals-react`, jsdom и Zod; тесты идут на `node:test`.

```bash
make setup                    # установка из lockfile: npm ci --ignore-scripts
npm run task -- list          # все поддерживаемые задачи с описаниями
npm test                      # весь обычный набор тестов
npm run task -- d01:demo      # только macOS: физическая песочница, JSON и HTML
npm run task -- d01:replay    # детерминированный повтор, без сети и подпроцессов
npm run task -- replay --evaluation-version eval-v1.1.0 # повтор официальных доказательств
```

`d01:demo` записывает бандл доказательств в
`artifacts/evaluation/BG-D01-VERTICAL-SLICE.html` — откройте его, чтобы увидеть, что
именно получает инженер.

Полное воспроизведение с чистого окружения, включая базовое плечо, зафиксированный
официальный прогон, ожидаемый вывод, время и стоимость — в `docs/REPRODUCTION.md`.

**Ограничение по платформе.** Изолирующий раннер использует macOS `/usr/bin/sandbox-exec`,
чтобы запретить сетевой выход поверх модели разрешений Node. На других платформах он
падает закрыто, а не ослабляет изоляцию молча. Детерминированный повтор работает везде.

## Как это устроено

Оба плеча получают одного и того же неизменяемого кандидата, одни и те же видимые входные
данные, одну и ту же среду и ровно одну попытку.

| | Базовое плечо | BeyondGreen |
|---|---|---|
| Входные данные | кандидат, компиляция, видимые легаси-тесты | те же самые |
| Метод | принять, если компиляция и все видимые тесты прошли | риск-инвентарь → выведенные пробы → независимое исполнение |
| Видимость оракула | отсутствует | отсутствует, пока вердикт не стал неизменяемым |

Основную часть результата дают четыре решения.

**Оракул — это отдельный процесс, а не флажок.** Плечо не может перечислить, прочитать,
захэшировать или прощупать ошибками закрытый пакет верификатора, а встречная проба
доказывает, что и оценщик не может прочитать кандидатов. Оба отказа утверждаются тестами,
а не предполагаются.

**`K=0`.** Ноль раундов обратной связи или починки от оценщика доходит до плеча, пока его
вердикт не стал окончательным. Процесс оценщика стартует только после того, как оба плеча
зафиксировали решение.

**Кандидат неизменяем.** Его хэш проверяется до и после каждого прогона. BeyondGreen
никогда не чинит кандидата во время оцениваемого прогона: как только объект оценки
изменился, вердикт больше нельзя сверить с фиксированной эталонной разметкой.

**Каждое утверждение привязано к записанному доказательству.** Канонический JSON, цепочка
хэшей поверх записи рассуждения и офлайновый повтор, который независимо перестраивает и
JSON, и HTML и отвергает подмену.

Архитектура, идентификаторы требований и полный контракт — в `docs/PROJECT_SPEC.md`.

## Главный вывод

Изоляция оракула в отдельном процессе — это то, что делает вердикт проверяемым, но она
не убирает риск, а переносит его: все сорвавшиеся официальные прогоны падали в
инфраструктуре вокруг этой границы (сначала pre-arm launcher, потом observer bridge,
потом evaluator transcript) и ни один — в рассуждении агента, поэтому граница процессов
требует такого же проверяемого словаря операций, их количества и схем, как и код,
который она судит.

Доказательства: `docs/IMPROVEMENT_CHANGELOG.md`, начиная с ITR-043.

## Границы применимости и честные ограничения

- Бенчмарк синтетический. Фикстуры написаны независимо друг от друга, но это не
  продакшн-код, и перенос на реальные репозитории не продемонстрирован.
- Версия 1 покрывает только миграцию React со state на сигналы.
- В официальном запуске использован адаптер `codex-exec-jsonl-v1` с моделью
  `gpt-5.6-sol`: по одному вызову на каждого кандидата BeyondGreen и без повторов.
  Маржинальная стоимость в долларах и стабильное число токенов не измерялись.

## Заметки для владельца, которых нет в английской версии

**Что изменилось против прежнего README.** Прежний открывался дедлайном челленджа,
контрактами чистой комнаты, преflight-чеклистом и строками вида `SES-20260830-003`

Прежний README сохранён в `tmp/README-before-judge-rewrite.md`, папка в gitignore.

**Порядок разделов выбран под рубрику.** Сначала продукт и пользователь — это критерий
Problem & User Value на 15 баллов. Затем результаты — Measured Improvement на 15 баллов;
таблица стоит выше быстрого старта намеренно, чтобы судья увидел числа до того, как решит,
запускать ли что-то. Затем одна команда — Reproducibility. Раздел «Как это устроено»
сведён к четырём решениям вместо описания модулей, потому что рубрика спрашивает именно
«какие проектные решения помогли агенту решить задачу».

**Раздел честных ограничений добавлен намеренно.** Признать синтетичность бенчмарка самому
сильнее, чем ждать, пока это заметит судья.

**Незаполненных числовых мест больше нет.** Метрики и сведения о живом адаптере взяты
из завершённого `POSTDECISION-004`. Публичное видео загружено на YouTube и Vimeo;
основная YouTube-ссылка проверена без входа. Открыты только финальный независимый
checkpoint и окончательный ZIP.

сорвавшихся прогона классифицированы как pre-arm infrastructure failure (`RUN-001`),
observer failure (`POSTDECISION-002`) и evaluator failure (`POSTDECISION-003`); ни один
не был отказом рассуждения плеча. Утверждение остаётся верным независимо от финальных
чисел.
